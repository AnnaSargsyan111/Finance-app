## Addendum: keyboard-submission finding, resolved by main (2026-09-22)

I (main) re-tested the "inconclusive" keyboard-submission finding above using a different browser-automation tool (real key events on the Log In form). Result: **Enter DOES submit the form** - a genuine `POST /api/auth/sign-in` request fired and returned `401`, confirmed via the network log. So the broad, potentially-Blocker worry above (forms not keyboard-submittable at all) is **not reproduced** and can be ruled out.

However, the same test surfaced a real, narrower bug: with wrong credentials, a **mouse click** on "Log in" shows "Email or password is incorrect.", but pressing **Enter** submits the identical form and gets the identical `401` response, yet shows no error message at all - the user is left looking at an unchanged, blank-feeling form. Filed as **QA-005 [Minor]** in `qa/defects.md` (owner: Frontend). Sign-up and the investment-amount step were not re-tested with this method and should be spot-checked for the same click-vs-Enter gap.

Net effect on the exit-criteria conditions below: condition (a) is resolved (no site-wide keyboard block), replaced by the narrower QA-005; condition (b) becomes "triage four open Minor defects" (QA-001, QA-003, QA-004, QA-005).

## Recommendation on §12.6 exit criteria
§12.6 requires: all AC-B/AC-F pass, no Blocker/Major open, fixtures committed, test report per area.

- **My overall recommendation: the prototype meets the §12.6 exit criteria for Backend/Frontend acceptance testing purposes** (no Blocker/Major open), **conditional on** (a) a human manually confirming keyboard Enter/Space submits the sign-up, log-in and investment-amount forms in a real browser before calling AC-F7 fully satisfied, and (b) triaging the three open Minor defects (none are release-blocking on their own).
